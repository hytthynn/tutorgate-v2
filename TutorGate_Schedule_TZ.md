# Техническое задание: расписание и рабочая статистика TutorGate

**Версия:** 1.0  
**Проект:** TutorGate v2  
**Статус:** итоговое ТЗ на реализацию  
**Базовый стек проекта:** Next.js 16 App Router, React 19, TypeScript strict, Supabase/PostgreSQL/RLS, Tailwind CSS v4, shadcn/Radix, date-fns, Recharts.

---

## 1. Цель задачи

Заменить существующую заглушку раздела «Расписание» полноценным недельным календарём занятий и подключить реальные данные расписания к существующему разделу «Статистика».

Расписание должно работать для трёх ролей:

- **tutor** — видит и полностью управляет только своим расписанием;
- **admin** — в разделе расписания работает как обычный репетитор и управляет только своим расписанием; интерфейс просмотра расписаний других репетиторов на этом этапе не реализуется;
- **student** — видит только свои занятия, не может создавать, изменять, переносить, отмечать или удалять их; по нажатию может открыть карточку занятия в режиме просмотра.

Администратор при этом сохраняет существующие административные возможности в других разделах, включая общую статистику и фильтр статистики по репетиторам.

## 2. Что уже есть в проекте и должно быть переиспользовано

В текущем проекте:

- `src/features/schedule/page.tsx` содержит заглушку расписания;
- маршруты `/student/schedule`, `/tutor/schedule`, `/admin/schedule` уже направлены на общий feature расписания;
- `src/features/statistics/service.ts` уже задаёт контракт `StatisticsQuery -> StatisticsResult`, но datasource возвращает нули;
- `src/components/statistics/statistics-view.tsx` уже содержит UI статистики: KPI, график, периоды `7 / 14 / 30 дней / свой период`, выбор метрики и административный фильтр по репетитору;
- `public.tutor_subjects` содержит разрешённые репетитору предметы;
- `public.student_tutor_assignments` содержит связи учеников и репетиторов;
- `public.app_settings.hourly_rate` содержит глобальную часовую ставку;
- роль `admin` уже имеет tutor capabilities на уровне продукта;
- текущий `.dashboard-content` ограничен `max-width: 1472px`, а `.schedule-panel` на больших экранах дополнительно ограничен `max-width: 1200px` — эти ограничения нельзя применять к календарной сетке расписания.

Реализация должна сохранять принятый в проекте принцип:

```text
page -> feature -> service/query -> Supabase
                    |
                    -> Server Actions для мутаций
```

Server Components остаются вариантом по умолчанию. Клиентскими должны быть только интерактивные части календаря, dialogs, context menu, drag-and-drop и локальное состояние выделения.

## 3. Зафиксированные продуктовые решения

Чтобы реализация была однозначной, принять следующие правила.

1. Неделя всегда идёт **с понедельника по воскресенье**.
2. На desktop одновременно видны **все 7 дней и все 24 часа** без горизонтальной и вертикальной прокрутки внутри календаря.
3. На мобильном отображается **один день**, при первом открытии — текущий день; дни недели можно переключать.
4. Текущий день определяется в выбранном пользователем сдвиге относительно МСК.
5. Текущая временная линия также строится в выбранном сдвиге относительно МСК.
6. Сетка взаимодействия имеет шаг **5 минут**. В форме время начала разрешено вводить с точностью до **1 минуты**.
7. Длительность занятия — целое число минут, **от 1 до 600 включительно**.
8. Пересечения занятий **запрещены**:
   - один репетитор не может иметь два занятия с пересекающимся временем;
   - один ученик не может иметь два занятия с пересекающимся временем;
   - соседние интервалы `10:00–11:00` и `11:00–12:00` допустимы.
9. В форме занятия ученик выбирается только из учеников, назначенных текущему репетитору хотя бы по одному предмету.
10. Предмет выбирается из **всех активных предметов, разрешённых текущему репетитору в `tutor_subjects`**. Предмет не обязан совпадать с предметом, по которому ученик был назначен репетитору.
11. Добавление нового занятия выполняется **только кнопкой «Добавить занятие»**. Клик, двойной клик, выделение пустой области и drag по пустой сетке не создают занятия.
12. Один клик по занятию выделяет его. Повторный клик по уже выделенному занятию открывает редактирование. Для ученика повторный клик открывает режим просмотра.
13. Прямоугольное выделение пустой области календаря используется для **множественного выбора занятий**, попавших в выделенную область. Оно не создаёт временной слот.
14. `Delete` удаляет все выбранные занятия сразу, без подтверждения.
15. Нажатие средней кнопки мыши на занятии переключает статус `проведено / не проведено`.
16. `проведено` — это единственный статус, по которому занятие попадает в фактическую статистику.
17. Drag-and-drop изменяет только дату и время начала. Длительность сохраняется.
18. После drag-and-drop время назначения привязывается к ближайшей 5-минутной отметке.
19. Drag-and-drop разрешён между днями и через границы недели. При удержании занятия у левого/правого края календаря должна автоматически открываться предыдущая/следующая неделя.
20. Все рабочие изменения расписания сохраняются в БД сразу. При ошибке оптимистическое изменение откатывается.
21. Кнопки «Отменить» и «Вернуть» на этом этапе видимы, но `disabled`; история действий и Undo/Redo не реализуются.
22. Кнопка «Бинды» только показывает действующие сочетания мыши/клавиатуры. Переназначение сочетаний не реализуется.
23. В контекстном меню отсутствует пункт «Приостановить».
24. Пункты «Перенести…», «Заниматься с…», «Отчёт по ученику» показываются как будущие функции, но disabled и ничего не выполняют.
25. Для недельного счётчика:
   - количество занятий относится к неделе, в которой находится **момент начала** занятия;
   - часы считаются по фактической части занятия, попавшей в отображаемую неделю.
26. Для статистики занятие считается один раз в день его начала, а часы и заработок при пересечении полуночи распределяются между календарными днями пропорционально фактической длительности в каждом дне.
27. Плановая статистика не нужна. В статистику входят только проведённые занятия.

# 4. UI расписания

## 4.1. Общая компоновка desktop

Страница расписания должна занимать всю доступную ширину области справа от sidebar.

Для расписания необходимо снять существующие ограничения:

- не применять `max-width: 1472px` к рабочей области календаря либо сделать schedule-specific full-width layout;
- удалить/переопределить `.schedule-panel { max-width: 1200px; }`;
- календарь растягивается на `width: 100%` доступного dashboard viewport.

Страница состоит из:

1. заголовка «Расписание»;
2. панели управления;
3. компактной строки недельной сводки;
4. заголовков 7 дней;
5. 24-часовой сетки;
6. слоя занятий;
7. слоя выделения;
8. линии текущего времени.

Календарь должен занимать оставшуюся высоту viewport так, чтобы весь диапазон `00:00–24:00` был виден одновременно. Внутреннего вертикального скролла у сетки быть не должно.

Высота одного часа вычисляется динамически:

```text
calendarBodyHeight / 24
```

Позиционирование занятия и текущего времени вычисляется в процентах от 1440 минут суток, а не через фиксированную высоту строки.

## 4.2. Сетка времени

Слева находится узкая колонка времени.

Обязательные подписи:

```text
00:00
01:00
02:00
...
23:00
24:00
```

Каждый час отделяется горизонтальной линией. Допускается более слабая линия на `:30`, если она не ухудшает читаемость. Линии каждые 5 минут визуально рисовать не требуется — шаг 5 минут используется для drag/drop и расчёта позиции.

Вертикально календарь делится на 7 равных колонок:

```text
Пн | Вт | Ср | Чт | Пт | Сб | Вс
```

В заголовке дня отображать:

- короткое название дня недели;
- число;
- короткое название месяца при необходимости.

Пример:

```text
Пн 31 авг
Вт 1 сен
Ср 2 сен
```

## 4.3. Текущий день

Если текущая дата попадает в открытую неделю, соответствующая колонка должна визуально выделяться:

- отличающийся фон заголовка;
- слабый фон всей колонки либо акцентная вертикальная/верхняя граница;
- визуально в рамках существующей warm mocha системы, без glow и тяжёлых теней.

Если открыта не текущая неделя, текущий день не выделяется.

## 4.4. Полоса текущего времени

Если текущая дата присутствует среди отображаемых дней, поверх её колонки рисуется горизонтальная линия текущего времени.

Требования:

- позиция обновляется автоматически не реже одного раза в минуту;
- слева от линии допускается небольшая точка/маркер;
- линия не должна блокировать клики по занятиям;
- при смене сохранённого сдвига МСК позиция и текущий день пересчитываются немедленно.

Если открыта другая неделя, линия не показывается.

# 5. Панель управления расписанием

## 5.1. Desktop

Панель должна содержать:

```text
[Год] [Месяц] [Неделя] [←] [→] [Текущая]
[Сдвиг МСК]
[Бинды] [Отменить] [Вернуть]
[Добавить занятие]
```

Конкретное визуальное расположение можно адаптировать по ширине, но функциональная группировка должна сохраняться.

### Год

Select выбора года.

При изменении года выбранный месяц сохраняется, если это возможно, а список недель перестраивается.

### Месяц

Select из 12 месяцев.

### Неделя

Select содержит только недели, которые **хотя бы одним днём пересекаются с выбранным месяцем**.

Пример для сентября 2026:

```text
31 авг — 6 сен
7 сен — 13 сен
14 сен — 20 сен
21 сен — 27 сен
28 сен — 4 окт
```

То есть первая и последняя недели месяца могут начинаться/заканчиваться в соседнем месяце.

При смене месяца по умолчанию выбирается первая неделя, пересекающая выбранный месяц, если текущая выбранная неделя с ним уже не пересекается.

### Стрелки недели

- `←` — предыдущая календарная неделя;
- `→` — следующая календарная неделя.

При переходе через месяц/год соответствующие select должны обновляться автоматически.

### Кнопка «Текущая»

Одним нажатием:

- открывает неделю, в которой находится текущая дата в сохранённом сдвиге МСК;
- обновляет год;
- обновляет месяц;
- обновляет week select;
- на мобильном выбирает текущий день.

### URL-состояние

Открытая неделя должна быть отражена в URL, чтобы работали refresh, Back/Forward и deep link.

Рекомендуемый канонический query-параметр:

```text
?week=2026-08-31
```

где значение — понедельник открытой недели в формате `YYYY-MM-DD`.

Год/месяц/week select являются UI-представлением этого значения и не обязаны храниться отдельными query-параметрами.

Некорректный `week` должен безопасно заменяться текущей неделей.

# 6. Сдвиг относительно МСК

## 6.1. UI

Select:

```text
МСК−12
...
МСК−1
МСК
МСК+1
...
МСК+12
```

Шаг — 1 час. Значение по умолчанию — `МСК` (`0`).

## 6.2. Хранение

Сдвиг хранится индивидуально для каждого пользователя и сохраняется между сессиями.

Рекомендуемое поле БД:

```text
msk_offset_hours smallint not null default 0
check (msk_offset_hours between -12 and 12)
```

Нельзя хранить дату/время занятия как локальную строку.

В БД время занятия хранится как абсолютное значение `timestamptz`.

Правило преобразования:

```text
отображаемый UTC offset = UTC+03:00 + msk_offset_hours
```

Примеры:

```text
МСК    -> UTC+03:00
МСК+2  -> UTC+05:00
МСК-3  -> UTC+00:00
```

Смена сдвига не изменяет сам объект занятия — меняется только его отображаемая дата/время.

## 6.3. Область действия

Сохранённый сдвиг используется для:

- расписания;
- определения текущего дня;
- линии текущего времени;
- преобразования дат формы добавления/редактирования;
- разбиения занятия по дням;
- недельных счётчиков;
- границ дат и точек графика статистики.

# 7. Недельная сводка

Над сеткой показывать:

```text
8 занятий · 10 ч 30 мин
```

Сводка относится к **отображаемой неделе**.

### Количество занятий

Занятие учитывается один раз, если его отображаемое локальное `starts_at` попадает в интервал понедельник 00:00 — следующий понедельник 00:00.

### Часы

Суммируется только фактическая часть каждого занятия, пересекающая открытую неделю.

Пример:

```text
Воскресенье 23:00 — понедельник 01:00
```

Для первой недели:

```text
1 занятие
1 час
```

Для следующей недели:

```text
0 занятий по правилу даты начала
1 час фактического времени
```

В недельную сводку входят и проведённые, и ещё не проведённые занятия, потому что это сводка расписания, а не фактическая статистика.

# 8. Добавление занятия

## 8.1. Открытие

Новое занятие можно создать только через кнопку:

```text
Добавить занятие
```

Никакие другие действия в сетке не должны создавать занятие.

## 8.2. Форма

Открывается Dialog в стиле текущего проекта.

Поля строго в следующем составе:

1. **Ученик** — select/combobox;
2. **День** — date input/date picker;
3. **Начало** — time input;
4. **Длительность, мин** — number input;
5. **Предмет** — select;
6. **Заметка** — textarea.

Кнопки:

```text
Отмена
Добавить
```

### Ученик

Для tutor/admin показывать только учеников, для которых существует хотя бы одна связь:

```text
student_tutor_assignments.tutor_id = current_user.id
```

Ученик не должен иметь возможности подставить произвольный чужой UUID через запрос.

### День

По умолчанию:

- текущая дата, если текущая дата находится в открытой неделе;
- иначе понедельник открытой недели.

Разрешено выбрать дату вне открытой недели. После успешного создания календарь должен перейти к неделе нового занятия и выделить созданное занятие.

### Начало

- пользователь может ввести любое корректное `HH:mm` с точностью до минуты;
- ограничение на кратность 5 минут в форме не применяется;
- при drag-and-drop итоговое время уже округляется до 5-минутной сетки.

### Длительность

```text
целое число
min = 1
max = 600
```

### Предмет

Показывать активные предметы, разрешённые текущему репетитору:

```text
tutor_subjects.tutor_id = current_user.id
AND subjects.is_active = true
```

Предмет не фильтруется по выбранному ученику.

### Заметка

- optional;
- максимум 4000 символов;
- видна репетитору, который ведёт занятие;
- видна администратору;
- никогда не передаётся ученику ни в UI, ни в payload ответа, ни через доступную ученику таблицу/представление.

## 8.3. Валидация

Проверять одновременно на клиенте для UX и обязательно на сервере/БД:

- ученик существует и имеет роль `student`;
- текущий пользователь имеет роль `tutor` или `admin`;
- ученик назначен текущему репетитору;
- предмет активен и присутствует в `tutor_subjects` текущего репетитора;
- дата корректна;
- время корректно;
- длительность `1..600`;
- новое занятие не пересекается с другим занятием текущего репетитора;
- новое занятие не пересекается с другим занятием выбранного ученика.

При ошибке пересечения показать понятное сообщение, например:

```text
Это время уже занято другим занятием.
```

Не показывать raw PostgreSQL/Supabase error.

# 9. Отображение занятия в календаре

Карточка занятия должна показывать минимум:

```text
Имя ученика
14:00–15:30
```

При достаточной высоте допускается третья строка с предметом.

Карточка позиционируется по абсолютному локальному времени внутри дня.

## 9.1. Цвет

Цвет хранится как логический key, а не произвольный HEX.

Допустимые значения:

```text
default
green
coral
gray
blue
```

Палитра должна визуально соответствовать приложенному референсу:

- default / сброс цвета;
- зелёный;
- коралловый;
- серый;
- голубой.

Рекомендуемые UI-значения, которые можно скорректировать под существующую палитру без изменения semantics:

```text
green  ~ #78C9A2
coral  ~ #D98B7A
gray   ~ #A79E94
blue   ~ #82ABD1
```

`default` использует стандартный цвет карточки TutorGate.

## 9.2. Выделенное занятие

Выбранная карточка должна иметь чёткое состояние selected:

- акцентная рамка;
- без изменения геометрии;
- доступно через `aria-selected=true` или эквивалентную семантику.

Клик по пустой сетке снимает выбор.

## 9.3. Проведённое занятие

Для проведённого занятия показывать явный маркер, например:

- иконку `Check`;
- слегка приглушённый фон/контраст;
- текст остаётся читаемым.

Не использовать зачёркивание как единственный признак состояния.

# 10. Занятие через полночь и границу недели

Длительность может быть до 600 минут, поэтому занятие может пересечь полночь.

Пример:

```text
23:00–01:30
```

Визуально это один объект БД, но в календаре он рендерится двумя сегментами:

```text
День 1: 23:00–24:00
День 2: 00:00–01:30
```

На первом сегменте показывать:

```text
Иван Иванов
23:00–01:30
```

На продолжении:

```text
↳ Иван Иванов
продолжение до 01:30
```

Оба сегмента:

- имеют один `lesson_id`;
- выделяются как одно занятие;
- изменение цвета применяется к обоим;
- отметка применяется к одному объекту целиком;
- удаление удаляет один объект;
- открывают один и тот же dialog;
- при drag-and-drop переносят весь объект с сохранением длительности.

## 10.1. Переход воскресенье -> понедельник

Если занятие начинается в воскресенье и заканчивается в понедельник следующей недели:

- в текущей неделе показывается воскресный сегмент до `24:00`;
- в следующей неделе показывается продолжение с `00:00` до фактического окончания;
- объект не дублируется в БД.

При открытии следующей недели продолжение должно быть видно, даже если `starts_at` лежит до начала этой недели. Следовательно, запрос расписания должен выбирать занятия по **пересечению временного диапазона**, а не только по `starts_at`.

# 11. Выделение в таблице

## 11.1. Курсор

Для tutor/admin над пустой областью календаря:


Над карточкой занятия курсор может меняться на `pointer`/`grab` в зависимости от состояния.

Для student crosshair не нужен, так как редактирование и массовое выделение недоступны.

## 11.2. Прямоугольное выделение

На tutor/admin:

1. `pointerdown` на пустом месте сетки;
2. drag мышью;
3. показывается полупрозрачный selection rectangle;
4. все карточки/сегменты, чьи визуальные прямоугольники пересекаются с selection rectangle, становятся выбранными;

# 14. Drag-and-drop занятия

## 14.1. Desktop

Tutor/admin может перетаскивать занятие:

- по времени внутри дня;
- между днями текущей недели;
- на предыдущую/следующую неделю.

Во время drag:

- карточка показывает preview нового положения;
- новое время округляется к ближайшей 5-минутной границе;
- длительность не меняется;
- предмет, ученик, заметка, цвет и статус не меняются.

## 14.2. Автопереход между неделями

Если во время drag указатель удерживается возле левого или правого края календаря, через короткую задержку порядка `400–600 ms`:

- слева — открыть предыдущую неделю;
- справа — открыть следующую неделю;
- продолжить drag того же занятия без отпускания pointer.

После drop вне исходной недели сохранение выполняется сразу.

## 14.3. Ошибка drop

Если новое время нарушает пересечение репетитора или ученика:

- Server Action/БД отклоняет изменение;
- карточка возвращается на исходное место;
- показывается toast/inline error;
- никаких частичных изменений не остаётся.

## 14.4. Мобильный Pointer Events

Реализацию строить на Pointer Events так, чтобы базовый drag работал и для touch. На touch требуется небольшой movement threshold, чтобы обычный tap не превращался в drag.

# 22. Модель данных

Добавить новую SQL migration. Существующие миграции не редактировать задним числом.

Рекомендуемая схема ниже задаёт требования; имена могут быть адаптированы, если сохраняется семантика.

## 22.1. `public.lessons`

```sql
create table public.lessons (
  id uuid primary key default gen_random_uuid(),
  tutor_id uuid not null references public.profiles(id),
  student_id uuid not null references public.profiles(id),
  subject_id uuid not null references public.subjects(id),
  starts_at timestamptz not null,
  ends_at timestamptz not null,
  duration_minutes smallint not null
    check (duration_minutes between 1 and 600),
  color text not null default 'default'
    check (color in ('default','green','coral','gray','blue')),
  completed_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  foreign key (tutor_id, subject_id)
    references public.tutor_subjects(tutor_id, subject_id)
    on delete restrict,

  check (ends_at > starts_at)
);
```

`ends_at` должен вычисляться сервером из:

```text
starts_at + duration_minutes
```

и защищаться от рассинхронизации. Предпочтительно триггером `BEFORE INSERT OR UPDATE`, который всегда переписывает `ends_at` и не доверяет значению клиента.

`completed_at IS NOT NULL` означает «занятие проведено».

При снятии отметки:

```text
completed_at = null
```

## 22.2. Индексы

Минимум:

```sql
create index lessons_tutor_time
  on public.lessons(tutor_id, starts_at, ends_at);

create index lessons_student_time
  on public.lessons(student_id, starts_at, ends_at);

create index lessons_completed_time
  on public.lessons(completed_at, starts_at)
  where completed_at is not null;
```

## 22.3. Защита от пересечений на уровне БД

Недостаточно проверять overlap только в TypeScript, потому что два параллельных запроса могут пройти проверку одновременно.

Использовать PostgreSQL exclusion constraints на half-open interval `[starts_at, ends_at)`.

При необходимости подключить extension `btree_gist`.

Смысл ограничений:

```sql
exclude using gist (
  tutor_id with =,
  tstzrange(starts_at, ends_at, '[)') with &&
)
```

и отдельно:

```sql
exclude using gist (
  student_id with =,
  tstzrange(starts_at, ends_at, '[)') with &&
)
```

Это должно гарантировать:

```text
10:00–11:00 + 11:00–12:00 -> OK
10:00–11:00 + 10:59–12:00 -> reject
```

## 22.4. Валидационный trigger

На insert/update дополнительно проверять:

- `tutor_id` имеет роль `tutor` или `admin`;
- `student_id` имеет роль `student`;
- существует хотя бы один `student_tutor_assignments` для пары `(student_id, tutor_id)`;
- `(tutor_id, subject_id)` существует в `tutor_subjects`;
- subject активен для создания/смены subject;
- `duration_minutes` валиден;
- `tutor_id` при пользовательских мутациях равен `auth.uid()`.

Историческое занятие не удалять автоматически, если предмет позже деактивирован.

# 23. Приватная заметка

Чтобы гарантировать, что student физически не сможет получить заметку через PostgREST, хранить её **отдельно** от публично читаемой student таблицы занятий.

## 23.1. `public.lesson_private_notes`

```sql
create table public.lesson_private_notes (
  lesson_id uuid primary key
    references public.lessons(id) on delete cascade,
  note text not null default ''
    check (char_length(note) <= 4000),
  updated_at timestamptz not null default now()
);
```

Пустую заметку можно либо хранить как `''`, либо удалять строку — выбрать один подход и использовать его последовательно.

## 23.2. Доступ

- student: **никакого SELECT**;
- tutor: read/write только для занятий, где `lessons.tutor_id = auth.uid()`;
- admin: может читать заметки; редактирование через текущий UI — только заметок собственных занятий, так как чужие расписания на этом этапе не редактируются.

Нельзя передавать поле note в student schedule query даже как `null`, если для этого пришлось бы открыть ученику исходную таблицу заметок.

# 27. Query расписания

Для открытой недели сначала вычислить абсолютный диапазон UTC из локальных границ выбранного сдвига:

```text
weekStart = Monday 00:00 local
weekEnd   = next Monday 00:00 local
```

Выбирать все занятия, которые **пересекают** диапазон:

```text
starts_at < weekEnd
AND ends_at > weekStart
```

Это обязательно для отображения продолжения занятия, начавшегося в предыдущей неделе.

### Tutor/admin own schedule

Дополнительное ограничение:

```text
tutor_id = auth.uid()
```

### Student

RLS и query:

```text
student_id = auth.uid()
```

### Связанные данные

Для карточек получить безопасные display fields:

- student full_name для tutor/admin;
- tutor full_name для student;
- subject name;
- lesson fields.

Не запрашивать Telegram identifiers.

Tutor/admin query отдельно получает private note только при открытии editor либо безопасно сервером для собственных занятий. Не требуется отправлять заметки для всех карточек календаря заранее.

# 29. Работа с временем

Нельзя полагаться на timezone браузера для бизнес-логики расписания.

Все вычисления выполняются явно в выбранном fixed offset относительно МСК.

Нужны отдельные чистые функции для:

```text
UTC instant -> local date/time for msk offset
local YYYY-MM-DD + HH:mm + offset -> UTC instant
startOfWeek(localDate)
endOfWeek(localDate)
getWeeksIntersectingMonth(year, month)
splitLessonByLocalDays(lesson, offset)
clipLessonToWeek(lesson, week, offset)
minutesFromLocalMidnight(instant, offset)
```

Эти функции должны иметь unit tests.

Не использовать implicit `new Date('YYYY-MM-DDTHH:mm')` без явной timezone семантики.

# 30. Optimistic UI

Для быстрых действий допускается и рекомендуется optimistic update:

- drag-and-drop;
- отметить/снять отметку;
- смена цвета;
- удаление.

Алгоритм:

```text
1. сохранить previous local state;
2. показать новое состояние;
3. вызвать Server Action;
4. success -> оставить + router.refresh/revalidate;
5. error -> вернуть previous state + toast.
```

Создание и полноценное редактирование через dialog можно подтверждать после ответа сервера, без обязательного optimistic insert.

Не допускать двойной отправки одной мутации во время pending state.

Нужно заменить `emptyDatasource()` в `src/features/statistics/service.ts` на реальный datasource занятий.

## 31.1. Сохраняемые возможности

- 7 дней;
- 14 дней;
- 30 дней;
- свой период;
- метрики `Заработок / Часы / Занятия`.

Admin:

Это не считается просмотром чужого **расписания**: отдельный календарь других репетиторов не реализуется, но агрегированная административная статистика остаётся.

## 31.2. Какие занятия входят

Только:

```text
completed_at is not null
```

Не проведённые, будущие и просто запланированные занятия не участвуют ни в одной фактической метрике.

## 31.3. Занятия

Метрика `lessons`:

- занятие считается ровно один раз;
- относится к локальной дате своего `starts_at` в текущем сохранённом сдвиге пользователя;
- если старт находится вне выбранного периода, занятие не увеличивает `lessons` этого периода, даже если его окончание пересекает период.

## 31.4. Часы

Метрика `hours`:

- длительность проведённых занятий переводится в часы;
- если занятие пересекает локальную полночь, минуты распределяются по соответствующим календарным дням;
- если занятие частично пересекает границу выбранного периода, учитывается только часть внутри периода;
- totals равен сумме points за период.

Пример:

```text
31.08 23:00 -> 01.09 01:00
```

График hours:

```text
31.08 -> 1.0
01.09 -> 1.0
```

## 31.5. Заработок

```text
earnings = hours * app_settings.hourly_rate
```

Используется **текущая глобальная ставка** на момент запроса статистики.

То есть изменение `hourly_rate` ретроспективно меняет расчёт старых периодов. Snapshot ставки на момент занятия в эту версию не входит.

При пересечении полуночи earnings распределяется по дням тем же способом, что и hours.

Финансовые значения округлять до 2 знаков после запятой после суммирования минут, чтобы минимизировать накопление ошибок.

## 31.6. Points

Для каждого календарного дня выбранного диапазона должен присутствовать point, включая дни с нулём.

Например период 7 дней всегда возвращает 7 points.

Формат display date оставить совместимым с текущим Recharts UI.

## 31.7. Admin фильтр

Если `tutorId` не задан:

- admin получает агрегат по всем tutor/admin занятиям, разрешённым RLS.

Если задан:

- проверить UUID;
- проверить, что профиль имеет роль `tutor` или `admin`;
- агрегировать только его занятия.

Tutor всегда принудительно получает `tutorId = auth.uid()` независимо от query string.

## 31.8. Реализация datasource

Для текущего объёма проекта допустимо:

1. на сервере вычислить абсолютные UTC-границы выбранного локального периода;
2. запросить проведённые занятия, которые пересекают этот диапазон:

```text
starts_at < periodEnd
AND ends_at > periodStart
AND completed_at IS NOT NULL
```

3. разрезать их по локальным дням в TypeScript;
4. сформировать `StatisticsPoint[]`;
5. прочитать `hourly_rate` под корректным RLS;
6. вычислить totals.

Не создавать фиктивные данные.

# 34. Accessibility и UX

Несмотря на mouse-heavy интерфейс, сохранить базовую keyboard accessibility.

Требования:

- карточка занятия должна быть focusable;
- focus-visible должен быть заметен;
- `Enter` открывает выбранное занятие;
- `Delete` работает только в безопасном schedule context;
- `Escape` закрывает menu/dialog или снимает selection;
- Dialog имеет focus trap через Radix;
- disabled «Отменить», «Вернуть» и future menu items корректно обозначаются как disabled;
- цвет не должен быть единственным способом определить проведённость;
- контраст текста в цветных карточках должен оставаться достаточным;
- при `prefers-reduced-motion` drag preview не должен зависеть от сложной анимации.

# 35. Производительность

Не использовать тяжёлую calendar-библиотеку только ради базового weekly grid, если она мешает требованиям полного 24-часового fit и кастомных interactions.

Текущих зависимостей React/date-fns достаточно для первой реализации. Drag/select можно реализовать через Pointer Events.

Требования:

- не делать отдельный запрос на каждую карточку;
- данные недели грузить одним schedule query + минимальными связанными запросами;
- private note загружать лениво при открытии editor;
- не re-render всего dashboard на каждое движение pointer;
- drag position хранить в локальном state/ref и коммитить только на drop;
- selection rectangle вычислять через bounding boxes уже отрисованных lesson segments.
