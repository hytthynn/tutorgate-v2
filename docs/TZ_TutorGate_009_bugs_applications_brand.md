# ТЗ: TutorGate — UI-баги, переносы занятий, заявки с модерацией и новый знак бренда

**Дата:** 05.09.2026  
**Проект:** TutorGate v2  
**Пакет:** 009  
**Основание:** архив `tutorgate-v2(4).zip`, 7 присланных скриншотов и уточнения заказчика.  
**Статус:** готово к реализации.

---

## 1. Цель пакета

В рамках одного пакета необходимо:

1. убрать лишний вертикальный скролл на страницах статистики;
2. исправить курсор над полями даты в модальных окнах и других местах интерфейса;
3. исправить визуальное отображение разрешённых пересечений занятий;
4. убрать согласованные элементы интерфейса со скриншотов;
5. исправить положение стрелок в кастомных select-компонентах расписания;
6. исправить логику удаления связанных занятий после переноса;
7. заменить текущий знак TutorGate на знак в форме кириллической буквы «П» с округлёнными углами, визуально напоминающий ворота;
8. реализовать полноценный раздел «Заявки» в админ-панели с Telegram-подтверждением, ручной модерацией и выдачей ссылки на регистрацию только после одобрения;
9. исправить отображение связки «репетитор · предмет» в списке учеников.

Все изменения должны сохранять текущую архитектуру проекта: Next.js 16 App Router, React 19, strict TypeScript, Supabase/PostgreSQL, RLS, Server Actions и существующие ограничения безопасности.

## 2. Подтверждённые решения заказчика

1. На странице статистики лишний вертикальный скролл нужно убрать и для `/admin/statistics`, и для `/tutor/statistics`.
2. Для `input[type="date"]` требуется **только изменение курсора** на `pointer`. Поведение открытия календаря менять не нужно.
3. Разрешённые пересечения должны отображаться друг поверх друга, а не в соседних колонках:
   - обычное + неактивное;
   - обычное + `coral`;
   - другие комбинации, которые разрешены текущими серверными правилами пересечений.
4. Со скриншотов удалить:
   - «Всё начинается с знаний» в sidebar;
   - текст «Заработок рассчитывается по проведённым часам. История сохраняется после удаления предметов.»;
   - `TutorGate / Репетиторы` в footer таблицы репетиторов;
   - `TutorGate / Ученики` в footer таблицы учеников;
   - у ученика в расписании — Undo, Redo и статус `Сохранено / Сохранение… / Не сохранено`.
5. У репетитора и администратора Undo/Redo и статус сохранения остаются.
6. Если удалить **новое перенесённое занятие**, исходное старое занятие должно восстановиться.
7. Если удалить **старое неактивное занятие-источник**, новое перенесённое занятие должно остаться и стать обычным занятием без статуса переноса.
8. Новый знак бренда — форма кириллической «П» с округлёнными углами, визуально похожая на ворота.
9. Flow заявки:
   - заявка отправлена;
   - пользователь подтверждает Telegram;
   - заявка уходит на ручную проверку администраторам;
   - администраторы получают Telegram-уведомление;
   - решение принимается **только в админ-панели**;
   - после принятия пользователь получает одноразовую ссылку регистрации;
   - после отклонения пользователь получает Telegram-уведомление.
10. Заявки сохраняются в истории.
11. В разделе заявок нужны:
   - разделение `Ученики / Репетиторы`;
   - статусы/вкладки `На рассмотрении / Принятые / Отклонённые`;
   - регистрационная ссылка на 24 часа;
   - кнопка выдачи новой ссылки после истечения предыдущей;
   - возможность повторно подать заявку тем же Telegram после отклонения.
12. Уведомление администраторам содержит роль, ФИО, `@username`, предметы и цель занятий/опыт преподавания. Кнопок принятия/отклонения в Telegram нет.
13. Стрелки select должны иметь одинаковый размер, правильное вертикальное выравнивание, фиксированный отступ справа и не должны накладываться на текст на desktop/mobile.
14. Связка назначения отображается в одну строку в формате:

   `Кефтеме Кефтеме Кефтеме · Русский язык`

# 4. Требование TG-009-01 — лишний скролл в статистике

## 4.1. Проблема

На `/admin/statistics` и `/tutor/statistics` появляется вертикальная полоса прокрутки даже в случаях, когда весь контент страницы визуально помещается в доступную высоту viewport.

## 4.2. Требуемое поведение

1. Если содержимое статистики помещается между верхней границей viewport и нижней границей страницы, вертикального scroll bar быть не должно.
2. Если контента действительно больше доступной высоты, обычный вертикальный скролл должен сохраняться.
3. Запрещено маскировать проблему глобальным `overflow: hidden` на `html`, `body` или всём dashboard, если это может сделать часть контента недоступной.
4. Не должно появиться горизонтального переполнения.
5. Исправление должно работать для обеих ролей: `tutor` и `admin`.

## 4.3. Область проверки

Проверить как минимум:

- 1366×768;
- 1440×900;
- 1920×1080;
- состояние с обычным периодом;
- состояние с `custom` и двумя date inputs;
- состояние с пустым графиком;
- состояние с заполненным графиком.

## 4.4. Acceptance criteria

- при физически помещающемся контенте `document.documentElement.scrollHeight <= clientHeight` с допустимой разницей округления не более 1 px;
- при реальном переполнении страница остаётся прокручиваемой;
- layout статистики не прыгает при смене периода/метрики.

# 5. Требование TG-009-02 — курсор над датами

## 5.1. Проблема

В текущем CSS присутствует правило:

```css
input[type="date"],
input[type="date"]::-webkit-calendar-picker-indicator {
  cursor: text;
}
```

Из-за этого date input выглядит как обычное текстовое поле.

## 5.2. Требуемое поведение

1. Над всей видимой областью `input[type="date"]` курсор должен быть `pointer`.
2. Над calendar picker indicator курсор также должен быть `pointer`.
3. Не изменять механику клика и открытия нативного календаря.
4. Не добавлять принудительный `showPicker()` по клику на поле.
5. Сохранить keyboard navigation и нативную доступность date input.

## 5.3. Где проверить

Минимально:

- custom period в статистике;
- модалка «Сможет заниматься с»;
- все вновь добавленные date inputs, если они появятся в рамках этого пакета.

# 6. Требование TG-009-03 — визуальное наложение разрешённых занятий

## 6.1. Проблема

База и бизнес-правила уже разрешают часть пересечений, но клиентская функция визуального layout `overlapLanes()` делит любые пересекающиеся интервалы по ширине. Поэтому обычное занятие и неактивное/красное визуально стоят рядом, хотя должны занимать одну временную колонку и накладываться.

## 6.2. Канонические правила конфликтов

Сохраняются текущие правила пакета 008:

| Пара | Серверный конфликт | Визуальное поведение |
|---|---:|---|
| normal ↔ normal | запрещён для одной конфликтующей пары tutor/student | не должен возникать; при defensive render допустимо lane-разделение |
| normal ↔ coral | разрешён | **накладывать** |
| coral ↔ coral | запрещён для одной конфликтующей пары tutor/student | не должен возникать; при defensive render допустимо lane-разделение |
| active ↔ inactive | разрешён | **накладывать** |
| inactive ↔ inactive | разрешён | **накладывать** |

`gray` остаётся обычным активным цветом и относится к normal conflict class.

## 6.3. Требуемое изменение layout

1. Lane-алгоритм должен учитывать `conflictClass()` / фактическую конфликтность, а не только временное пересечение.
2. Карточки, которые сервер разрешает размещать в одно и то же время, должны получать полную доступную ширину дня.
3. Для разрешённого пересечения обе карточки находятся в одинаковой горизонтальной области и визуально накладываются по времени.
4. Карточки должны оставаться кликабельными. Необходимо обеспечить понятный `z-index`/порядок слоёв.
5. При наложении активное обычное занятие должно быть доступно для взаимодействия; неактивное не должно полностью перекрывать его hit area.
6. Выделенная/перетаскиваемая карточка должна подниматься выше остальных существующими состояниями `is-selected` / `is-dragging`.
7. Нельзя ослаблять серверные exclusion constraints ради визуального исправления.

## 6.4. Рекомендуемый порядок слоёв

От нижнего к верхнему:

1. неактивное;
2. `coral`;
3. обычное активное;
4. selected;
5. dragging;
6. current-time line и selection rectangle согласно существующей логике.

Если текущий UX требует иной порядок внутри одинакового класса, главное условие — активное занятие нельзя сделать недоступным из-за неактивной карточки.

## 6.5. Acceptance criteria

- normal + inactive на одном времени: обе карточки используют практически полную ширину day-column, не делятся 50/50;
- normal + coral: то же;
- создание/drag/paste по-прежнему используют существующие серверные правила конфликтов;
- нет регрессии midnight segments;
- нет горизонтального overflow.

# 9. Требование TG-009-06 — удаление перенесённых занятий

## 9.1. Термины

- **source** — исходное занятие, которое при переносе получило `inactive_reason = 'transferred'`;
- **target** — новое занятие, созданное переносом, `is_transfer_target = true`, с `transfer_source_id` и snapshot времени источника.

## 9.2. Сценарий A — удаляется target

### Сейчас

Target удаляется обычным `DELETE`, source остаётся неактивным `transferred`.

### Должно быть

Если пользователь удаляет target:

1. target удаляется;
2. связанный source восстанавливается;
3. у source снимается причина `transferred`;
4. source снова становится обычным занятием в исходном времени;
5. после снятия `transferred` для source заново применяется текущая availability-логика:
   - если по правилу `Сможет заниматься с` исходная дата всё ещё должна быть неактивной — source получает `available_from`;
   - иначе `inactive_reason = null`;
6. `completed_at` не должен самопроизвольно восстанавливаться из старого состояния переноса, если оно было сброшено при переносе;
7. операция выполняется атомарно: нельзя получить состояние «target уже удалён, source ещё transferred».

## 9.3. Сценарий B — удаляется source

Если пользователь удаляет старое неактивное source-занятие:

1. source удаляется;
2. target остаётся на месте;
3. target превращается в обычное занятие:
   - `is_transfer_target = false`;
   - `transfer_source_id = null`;
   - `transfer_source_starts_at = null`;
4. после этого target можно переносить обычной командой «Перенести…», если остальные правила это разрешают;
5. в UI больше не показывается `↪`, «Перенесённое занятие» и «Перенесено с …».

## 9.4. Сценарий C — массовое удаление

Если в одной delete-команде присутствуют связанные source/target или несколько переносов:

- результат должен быть детерминированным и атомарным;
- удаление обеих сторон одной и той же transfer-пары означает, что обе записи удаляются и ничего не восстанавливается;
- для target, source которого не входит в delete-набор, source восстанавливается;
- для source, target которого не входит в delete-набор, target отвязывается и становится обычным;
- нельзя обновлять запись, которая одновременно должна быть удалена этой же командой.

## 9.5. Сервер — обязательное изменение

Логику реализовать в `public.schedule_command(jsonb)` / новой миграции, а не только в optimistic UI.

Причины:

- сервер — канонический источник;
- undo/redo и конкурирующие запросы должны видеть согласованное состояние;
- клиент не должен сам собирать небезопасные каскадные writes.

## 9.6. Optimistic UI

Клиентский `remove()` должен оптимистически моделировать тот же результат:

- удаление target немедленно показывает restored source;
- удаление source немедленно показывает обычный target;
- после ответа сервера состояние заменяется каноническим `result.lessons`;
- при ошибке откатывается целиком.

## 9.7. Undo/Redo

Обе операции должны корректно попадать в существующую signed snapshot history:

- Undo удаления target возвращает target и снова делает source `transferred`;
- Undo удаления source возвращает source и снова помечает target transfer-target;
- Redo повторяет соответствующий результат.

# 10. Требование TG-009-07 — новый логотип и favicon

## 10.1. Общая идея

Текущий Lucide `PanelLeftClose` заменить на собственный знак TutorGate.

Знак должен выглядеть как кириллическая буква **«П»**, одновременно визуально восприниматься как **ворота**.

## 10.2. Геометрия

1. Две вертикальные стойки + верхняя горизонтальная перекладина.
2. Нижняя часть открыта.
3. Верхние внешние углы — заметно округлённые.
4. Внутренние переходы также не должны быть острыми.
5. Толщина линий/формы визуально равномерная.
6. Знак должен хорошо читаться в 16×16, 24×24 и 32×32.
7. Не использовать букву из системного шрифта как favicon — нужен самостоятельный SVG/vector mark.
8. Не использовать gradient, glow или тяжёлые тени.

## 10.3. Где заменить

Минимально:

- `src/components/shared/brand.tsx`;
- sidebar;
- mobile header;
- public header, где используется `Brand`;
- favicon/app icon через Next.js metadata icon (`src/app/icon.svg` либо эквивалентный поддерживаемый вариант).

Текст `TutorGate.` рядом со знаком оставить.

## 10.4. Цвета

Сохранить текущую цветовую систему:

## 11.6. Принятие заявки

При нажатии `Принять`:

1. сервер повторно проверяет текущего пользователя через `getUser` и роль `admin`;
2. блокирует/проверяет заявку в транзакции;
3. убеждается, что status = `pending_review`;
4. создаёт новый cryptographically random registration token;
5. в БД хранит только SHA-256 hash token;
6. срок — ровно 24 часа;
7. заявка получает:
   - `status = 'approved'`;
   - `reviewed_at`;
   - `reviewed_by`;
   - при необходимости отдельный `approved_at`;
8. после успешной транзакции пользователю отправляется Telegram-сообщение:

```text
Ваша заявка в TutorGate принята.

Завершите регистрацию:
<APP_URL>/register?token=...

Ссылка действует 24 часа и может быть использована один раз.
```

9. Ссылка всегда строится только через `APP_URL`.
10. Raw token нельзя логировать.

### Ошибка Telegram delivery

Если решение уже сохранено, но отправить сообщение не удалось:

- не откатывать принятие заявки;
- показать администратору понятное предупреждение;
- дать возможность отправить новую ссылку;
- не показывать raw token в UI.

## 11.7. Новая регистрационная ссылка

Для `approved` заявки добавить action:

`Отправить новую ссылку`

Кнопка обязательна, когда последняя registration link истекла. Допустимо также показывать её после известной ошибки доставки.

При выдаче новой ссылки:

1. все прежние **неиспользованные** registration tokens этой заявки инвалидируются (`used_at` либо отдельный revoked marker);
2. создаётся один новый token на 24 часа;
3. пользователю отправляется новая Telegram-ссылка;
4. status заявки остаётся `approved`;
5. история решения не меняется;
6. после успешной регистрации status становится `registered`.

После `registered` кнопку новой ссылки не показывать.

## 11.8. Отклонение заявки

При нажатии `Отклонить`:

1. сервер проверяет роль admin;
2. заявка должна быть `pending_review`;
3. status → `rejected`;
4. сохраняются `reviewed_at`, `reviewed_by`, при необходимости `rejected_at`;
5. пользователю отправляется Telegram:

`Ваша заявка в TutorGate отклонена. Вы можете подать новую заявку позже.`

Причину отклонения в этом пакете вводить не требуется.

### Повторная заявка

После `rejected` тот же Telegram account должен иметь возможность:

- заполнить `/apply` заново;
- подтвердить тот же Telegram user id/chat id;
- создать новую независимую заявку.

Старая rejected-заявка остаётся в истории.

## 11.9. Изменения БД

Нужна новая миграция после `202609050007_schedule_features.sql`, например:

`supabase/migrations/202609050008_applications_review_and_ui_fixes.sql`

### Application status

Расширить enum минимум статусами:

- `pending_review`;
- `approved`;
- `rejected`.

Существующий `telegram_verified` больше не должен означать «можно регистрироваться».

При миграции production data:

- существующие реально зарегистрированные остаются `registered`;
- незарегистрированные `telegram_verified` необходимо перевести в согласованное безопасное состояние. Рекомендуемо — `pending_review`, без автоматического одобрения; существующие неиспользованные registration tokens таких заявок должны быть инвалидированы либо гарантированно стать непригодными после новой проверки `status = approved`.

### Новые поля applications

Добавить минимум:

```text
reviewed_at timestamptz null
reviewed_by uuid null -> profiles(id)
approved_at timestamptz null
rejected_at timestamptz null
```

Допустима более компактная схема, если она сохраняет те же возможности аудита.

### Уникальность Telegram

Текущие unique constraints на `applications.telegram_user_id` и `telegram_chat_id` мешают повторной заявке после отклонения.

Необходимо заменить их на модель, в которой:

- активная заявка резервирует Telegram identity;
- `rejected` и `expired` не блокируют новую заявку;
- `profiles.telegram_user_id/chat_id` по-прежнему остаются уникальными и блокируют повторную регистрацию уже существующего пользователя;
- история rejected-заявки не требует стирания Telegram identity только ради снятия unique constraint.

Рекомендуемый вариант — partial unique indexes для активных application statuses.

### Registration token

`confirm_telegram()` больше **не создаёт** token с `purpose='registration'`.

Registration token создаётся только admin review action после `approved`.

### Registration trigger

`private.register_auth_user()` должен принимать только заявку, которая:

- Telegram verified;
- имеет status `approved`;
- имеет валидный одноразовый registration token;
- ещё не registered/rejected.

После успешной регистрации:

- status → `registered`;
- `registered_at = now()`;
- registration token помечается used;
- существующая атомарность создания auth user/profile сохраняется.

### Expiration logic

Не переписывая migration 004, в новой migration выполнить `CREATE OR REPLACE`/эквивалентное обновление `expire_old_applications` и связанной логики:

- истёкшая ссылка Telegram confirmation может переводить `pending_telegram` в `expired`;
- истёкший registration token **не переводит approved application в expired**;
- approved application сохраняется для resend.

## 11.10. Серверные actions / service functions

Добавить серверные операции:

```text
getAdminApplications(...filters)
approveApplicationAction(applicationId)
rejectApplicationAction(applicationId)
resendRegistrationLinkAction(applicationId)
```

Конкретные имена могут отличаться.

### Обязательные проверки

Каждая admin operation:

1. получает текущего пользователя через безопасный server auth flow;
2. проверяет `role === 'admin'`;
3. не доверяет role из client payload;
4. использует service RPC/transaction с повторной проверкой в БД;
5. проверяет допустимый status transition;
6. не принимает arbitrary chat_id, role или application status от клиента.

## 11.11. RLS и приватность

1. `applications` не открывать обычному authenticated SELECT напрямую.
2. Получение admin queue — через admin-only RPC/service layer либо строгое RLS-правило с проверкой admin.
3. Student/tutor не могут прочитать чужие заявки.
4. Telegram user id/chat id не отдавать в browser без необходимости. Для UI достаточно `telegram_username`.
5. Raw one-time token никогда не хранится в public table и не возвращается в admin client.
6. Все token hashes остаются в `private.one_time_tokens`.
7. Не логировать registration URLs, cookies и request body Telegram webhook.

## 11.12. Идемпотентность и конкуренция

Обязательные сценарии:

- Telegram повторно доставляет один и тот же update → заявка не дублируется, admin notifications не дублируются;
- два администратора одновременно нажали `Принять` → создаётся только одно решение;
- один нажал `Принять`, другой `Отклонить` → выигрывает первый зафиксированный transition, второй получает нейтральную ошибку «Заявка уже обработана»;
- double click `Принять` не создаёт две активные registration links;
- resend инвалидирует прежнюю неиспользованную ссылку;
- регистрация по старой ссылке после resend не работает;
- регистрация по уже использованной ссылке не работает.

# 12. Требование TG-009-09 — отображение «репетитор · предмет»

## 12.1. Проблема

В admin students table связка назначения выглядит визуально слитно/неаккуратно, например имя и предмет воспринимаются как неправильная строка.

Каждое назначение показывать строго в одну строку:

4. строка не переносится на вторую строку;

6. при недостатке места допускается ellipsis;
7. полное значение должно оставаться доступным через `title`/tooltip либо другой доступный способ;
8. приглушённый цвет предмета можно сохранить, но он не должен выглядеть как отдельная строка.

### Несколько назначений

Если у ученика несколько назначений, каждое назначение остаётся отдельной однострочной записью, записи располагаются вертикально с существующим небольшим gap.
