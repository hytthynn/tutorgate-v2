# Техническое задание: исправление багов и доработка расписания TutorGate

**Проект:** TutorGate v2  
**Дата ТЗ:** 05.09.2026  
**Основание:** текущий проект из архива `tutorgate-v2(1).zip`, приложенные скриншоты и согласованные уточнения.

---

## 1. Цель работ

Исправить UX- и функциональные проблемы в интерфейсе TutorGate, в первую очередь в расписании, административных формах и элементах выбора. Убрать лишние браузерные элементы управления, унифицировать выпадающие списки и уведомления, избавиться от полных перезагрузок расписания при работе с занятиями, реализовать «магнит» для предотвращения пересечений, физическое удаление предметов с сохранением истории занятий и автоматический перенос недельного расписания на новую неделю.

Работы должны выполняться без нарушения текущей ролевой модели, RLS, приватности заметок и статистики.

11. Проведённое занятие помечается текстовым символом `✓`.
12. Уведомления реализованы неоднородно: inline-сообщения и отдельный `.schedule-notice`.
13. Сейчас можно работать с будущими неделями, а автоматического переноса расписания на начало новой недели нет.

# 3. Функциональные требования

## FR-01. Убрать стрелки у числовых полей

### Требование

Во всех числовых полях интерфейса убрать браузерные кнопки `▲/▼` для изменения значения.

В частности это касается:

- ставки за час;
- длительности занятия;
- любых других существующих и будущих `input[type="number"]`.

### Поведение

- поле остаётся числовым;
- ручной ввод работает;
- ограничения `min`, `max`, `step` и текущая валидация сохраняются;
- управление клавиатурой не должно ломаться;
- изменение не должно затрагивать стрелку/chevron у выпадающих списков.

### Реализация

Добавить глобальный стиль для WebKit и Firefox либо общий UI-класс:

- `::-webkit-inner-spin-button` / `::-webkit-outer-spin-button` → скрыть;
- `appearance: textfield` для Firefox.

### Критерий приёмки

Ни в одном числовом поле проекта визуально нет системных spinner-кнопок.

## FR-02. Полное удаление предмета с сохранением истории занятий

### Согласованное бизнес-правило

При удалении предмета:

- предмет должен физически удаляться из текущих предметов;
- он должен исчезать из всех текущих назначений и списков;
- история уже созданных занятий должна сохраниться;
- в старых занятиях должно по-прежнему отображаться историческое название удалённого предмета.

Текущий soft-delete через `is_active=false` больше не является поведением операции «Удалить».

### Что удалить вместе с предметом

Перед физическим удалением предмета удалить актуальные связи:

- `student_tutor_assignments` по этому предмету;
- `tutor_subjects` по этому предмету;
- `application_subjects` по этому предмету;
- саму строку `subjects`.

Удаление должно выполняться атомарно в одной транзакции/RPC. Частичное состояние недопустимо.

### Сохранение истории занятий

Текущая схема не позволяет физически удалить `subjects`, потому что `lessons.subject_id` и составной FK на `tutor_subjects` удерживают предмет.

Необходимо изменить модель исторических занятий:

1. Добавить в `lessons` snapshot исторического имени, например:
   - `subject_name_snapshot text not null`.
2. Выполнить backfill для всех существующих занятий из `subjects.name`.
3. `lessons.subject_id` сделать допускающим `NULL`.
4. FK `lessons.subject_id -> subjects.id` изменить на `ON DELETE SET NULL`.
5. Убрать составной FK `lessons(tutor_id, subject_id) -> tutor_subjects`, который мешает удалению текущих назначений при наличии истории.
6. Проверку актуальности назначения выполнять в `private.validate_lesson()` для новых занятий и при изменении ученика/предмета.
7. Историческое название возвращать как:
   - актуальное `subjects.name`, если предмет существует;
   - иначе `subject_name_snapshot`.

`public.schedule_lesson_names()` должен поддерживать это поведение.

### Важное правило редактирования старого занятия

Если предмет уже удалён:

- старое занятие остаётся доступным для просмотра;
- название предмета показывается из snapshot;
- удалённый предмет нельзя выбрать в новом занятии;
- при редактировании исторического занятия можно сохранить остальные поля без обязательного восстановления удалённого предмета;
- если пользователь вручную меняет поле «Предмет», новый предмет обязан быть активным и назначенным.

Для этого Server Action/RPC редактирования должен уметь отличать «предмет не меняли» от выбора нового предмета.

### UI удаления

В подтверждении удаления заменить текущий текст про архив на явное предупреждение:

> Предмет будет полностью удалён из текущих назначений и списков. История уже созданных занятий сохранится.

После успешного удаления — success toast.

### Критерии приёмки

- после удаления строки предмета больше нет в `subjects`;
- предмет отсутствует в формах, фильтрах, заявках и назначениях;
- связанные текущие назначения удалены;
- старые занятия не удалены;
- старые занятия продолжают показывать исходное название предмета;
- статистика по старым проведённым занятиям не теряется.

## FR-07. Выбор дня недели в форме занятия + исправление заметки

Вместо него использовать dropdown «День» с семью днями недели выбранной недели.

Формат пункта:

- `Пн, 07.09`;
- `Вт, 08.09`;
- ...
- `Вс, 13.09`.

В value хранить реальную ISO-дату `YYYY-MM-DD`.

### Создание

Создание нового занятия разрешено только в текущей неделе согласно FR-13. Поэтому в новой форме список дней относится к текущей пользовательской неделе.

По умолчанию:

- если сегодня входит в текущую неделю — выбрать сегодня;
- иначе использовать понедельник текущей недели.

### Редактирование

При редактировании существующего занятия:

- dropdown содержит 7 дней недели, к которой относится редактируемое занятие;
- текущий день занятия выбран;
- изменение дня не должно превращаться в произвольный календарный выбор.

### 7.2. Поле «Заметка»

Исправить textarea:

- убрать системный угол/resize marker;
- `resize: none`;
- задать нормальную минимальную высоту;
- реализовать auto-grow по мере ввода;
- после достижения максимальной высоты включать внутренний scroll;
- не менять ограничение 4000 символов;

Рекомендуемые параметры:

## FR-08. Загружать все недели при открытии расписания и убрать refresh после операций

### Требование к загрузке

При первом открытии страницы расписания загрузить **все доступные пользователю занятия за всё время**, а не только текущую неделю.

Это означает:

- для tutor/admin — все собственные занятия;
- для student — все занятия этого ученика;
- без ограничения ±N месяцев/лет;
- сервер может читать базу пакетами, но клиент после initial render должен иметь полный набор карточек расписания.

Приватные заметки не требуется загружать для всех занятий заранее: они могут оставаться lazy-loaded при открытии карточки, так как не участвуют в переключении недель.

### Работа с неделями

После initial load:

- переключение недели выполняется только локально;
- смена года/месяца/недели не запускает повторный серверный запрос данных расписания;
- `router.refresh()` при недельной навигации убрать;
- URL `?week=...&day=...` можно продолжать синхронизировать через History API для deep-link/back/forward.

### Смена сдвига МСК

После изменения offset:

- сохранить preference на сервере;
- не выполнять полный refresh;
- пересчитать отображение уже загруженных UTC-дат локально;
- при ошибке вернуть старый offset и показать toast.

### CRUD без обновления таблицы

После:

- создания;
- редактирования;
- drag&drop;
- смены цвета;
- отметки «проведено»;
- снятия отметки;
- удаления

нельзя делать `router.refresh()` и нельзя визуально перезагружать всю таблицу.

Использовать локальное состояние с optimistic update либо обновление по нормализованному ответу Server Action.

### Контракт Server Actions

Server Actions должны возвращать достаточно данных для точечного обновления клиента, например актуальную `ScheduleLesson`, а не только `id`.

Минимально:

- create → вернуть созданное занятие с фактическим временем после магнита;
- update/move → вернуть обновлённое занятие;
- completed/color → вернуть изменённые поля или сущность;
- delete → вернуть удалённые `ids`.

`revalidatePath()` для будущего захода на статистику допустим, но текущий клиентский календарь не должен после этого вызывать refresh.

### Пагинация чтения

Поскольку данных может быть больше лимита Supabase/PostgREST:

- читать все строки пакетами, например по 500;
- продолжать запрос до пустой/неполной страницы;
- аналогично получать безопасные имена участников батчами;
- не обрезать историю молча.

### Критерии приёмки

- после открытия расписания переход между уже существующими неделями моментальный;
- в Network нет нового RSC/document запроса только из-за переключения недели;
- после создания занятия grid не мигает и не перезагружается;
- scroll position и пользовательское состояние не сбрасываются;
- новая карточка появляется сразу.

## FR-09. «Магнит» при перемещении занятий

### Бизнес-правило

Занятия **не могут накладываться друг на друга**.

При drag&drop пользователь может бросить занятие на занятое время, но вместо ошибки и отката система должна автоматически поставить его в ближайший свободный временной интервал.

### Базовая сетка

Сохранить существующий snap с шагом **5 минут**.

Сначала целевое время округляется к ближайшим 5 минутам, затем применяется поиск свободного интервала.

### Что считается конфликтом

Интервал `[start, end)` должен быть свободен одновременно:

1. у текущего репетитора;
2. у выбранного ученика.

То есть два занятия одного репетитора не пересекаются, и один ученик также не может находиться на двух занятиях одновременно даже у разных репетиторов.

Существующие PostgreSQL exclusion constraints `lessons_tutor_overlap` и `lessons_student_overlap` сохранить как окончательную защиту целостности.

### Алгоритм магнита

1. Получить желаемое время после 5-минутного snap.
2. Проверить весь интервал с учётом длительности занятия.
3. Если свободно — оставить его.
4. Если занято — искать ближайший свободный start с шагом 5 минут в обе стороны.
5. Выбирать только вариант, в который полностью помещается длительность занятия.
6. При одинаковом расстоянии до свободного интервала выбирать вариант **после** желаемого времени.
7. Start должен оставаться в выбранном пользователем дне; само занятие при большой длительности может завершиться после полуночи, как допускает текущая модель.
8. Если в этом дне подходящего старта нет — не переносить занятие и показать error toast «В этот день нет свободного интервала такой длительности.»

### Client + server

Client может показывать предварительный magnet-preview по известным ему занятиям.

Однако финальное решение обязательно принимает сервер/БД, потому что репетитор не видит чужие занятия выбранного ученика и возможны race conditions.

Рекомендуется вынести серверную логику в одну атомарную функцию/RPC, используемую для create/update/move.

### Результат

Если сервер скорректировал время:

- карточка должна оказаться в фактическом возвращённом времени;
- показать info/warning toast, например:
  - `10:30 занято — занятие поставлено на 11:00.`

При обычном свободном переносе дополнительный warning не нужен.

### Критерий приёмки

Перенос на занятую область больше не заканчивается сообщением «Это время уже занято» и откатом, если в этом дне существует свободный интервал.

## FR-10. Создание занятия в занятое время — автоматически поставить рядом

### Требование

Если пользователь создаёт занятие на время, которое уже занято, занятие всё равно должно быть создано, но в ближайшем свободном слоте.

Использовать **тот же алгоритм магнита, что и FR-09**.

Не создавать визуальные колонки с одновременными занятиями. Пересечения остаются запрещены.

### Пример

Есть занятие `10:00–11:00`.

Пользователь создаёт ещё одно длительностью 60 минут на `10:30`.

Система ищет ближайший 60-минутный свободный слот и создаёт занятие там, например `11:00–12:00`.

После сохранения:

- форма закрывается;
- карточка добавляется в локальное состояние без refresh;
- пользователь видит toast о фактическом времени, если оно было изменено магнитом.

### Дополнительно

Тот же серверный механизм желательно использовать при редактировании времени существующего занятия, чтобы поведение create/edit/drag было единообразным.

## FR-13. Запрет создания занятий в будущей неделе и автоматический перенос расписания

### 13.1. Запрет ручного создания в будущих неделях

Пользователь не может вручную создавать занятие на неделе, которая начинается позже текущей пользовательской недели.

«Текущая неделя» определяется по локальной дате пользователя с учётом его сохранённого `Сдвиг МСК`.

### UI

Если открыта будущая неделя:

- кнопку «Добавить занятие» сделать disabled;
- tooltip: `Занятия будущей недели появятся автоматически в начале недели.`;
- нельзя создать занятие через пустую область grid, горячую клавишу или иной обходной путь.

Server-side validation обязательна: нельзя полагаться только на disabled button.

### Перемещение/редактирование

Нельзя:

- drag&drop перенести занятие в будущую относительно текущей неделю;
- через редактирование изменить занятие так, чтобы его start попал в будущую неделю;
- вызвать Server Action напрямую с будущей датой и обойти UI.

Исторические занятия и текущая неделя продолжают работать в рамках существующих прав.

### Навигация

Навигация на будущую неделю разрешена для просмотра, но до момента её наступления она не должна заполняться вручную пользователем.

---

### 13.2. Автоматический перенос предыдущей недели на новую

Когда для репетитора/администратора начинается новая локальная неделя, расписание предыдущей недели автоматически переносится на новую.

**На уровне БД это должно быть копирование, а не физическое перемещение старых строк.**

Старые занятия обязательно остаются в истории, иначе будут сломаны история и статистика.

### Что копируется

Для каждого занятия, start которого находился в предыдущей локальной неделе владельца расписания:

- ученик;
- предмет, если он всё ещё существует и доступен;
- день недели;
- локальное время начала;
- длительность;
- цвет;
- приватная заметка.

Для новой строки:

- создаётся новый `id`;
- `starts_at` соответствует тому же дню недели и времени новой недели;
- `completed_at = NULL`;
- состояние нового занятия — «Запланировано»;
- `created_at/updated_at` новые.

### Что не переносить

Не создавать новую копию, если к моменту переноса:

- занятие было удалено из предыдущей недели;
- предмет физически удалён;
- назначение ученика этому репетитору/по предмету больше не действительно.

Историческая исходная строка при этом остаётся без изменений.

### Изменения после переноса

Перенос выполняется один раз.

Если после автоматического переноса пользователь отредактирует занятие прошлой недели, уже созданное занятие текущей недели автоматически не синхронизируется обратно.

Текущая неделя является новым самостоятельным набором занятий и, в свою очередь, станет источником для следующей недели.

### Идемпотентность

Повторный запуск job/RPC не должен создавать дубликаты.

Добавить служебное состояние, например:

`schedule_week_rollovers`

с уникальностью:

- `(tutor_id, target_week_start)`.

Перенос текущей недели должен выполняться в транзакции.

### Автоматический запуск

Нужен фоновой механизм, не зависящий от того, открыл ли пользователь страницу.

Рекомендуемый вариант:

- идемпотентная PostgreSQL function/RPC;
- запуск через Supabase Cron/pg_cron с небольшим интервалом, например каждые 5 минут;
- функция определяет для каждого tutor/admin локальную дату с учётом `user_schedule_preferences.msk_offset_hours` и проверяет необходимость rollover.

Дополнительно перед первой мутацией расписания текущей недели можно выполнять безопасный `ensure rollover` как fallback, чтобы пользователь не успел создать занятие до завершения фонового переноса.

### Конфликты при автоматическом переносе

Существующие exclusion constraints должны сохраняться.

Если по race condition целевой слот уже занят, автоматический перенос должен использовать тот же серверный алгоритм ближайшего свободного слота, что FR-09/FR-10, либо безопасно пропустить конкретный конфликт с записью результата. Предпочтительно использовать единый magnet resolver.

Нельзя отключать ограничения пересечения ради rollover.

### SLA

Новая неделя должна быть сформирована автоматически не позднее чем через **5 минут** после начала локальной недели владельца расписания.

### Критерии приёмки

- до начала следующей недели нельзя создать в ней занятие вручную;
- после наступления новой недели в ней появляются копии валидных занятий прошлой недели;
- предыдущая неделя остаётся в истории;
- completed state не переносится;
- повторный job не создаёт дубликаты;
- удалённые предметы/снятые назначения не порождают новые занятия;
- student видит новые занятия, созданные rollover соответствующих репетиторов.

# 4. Требования к серверной логике магнита

Чтобы FR-09, FR-10 и FR-13 не имели разного поведения, требуется единый server-side resolver.

## 4.1. Рекомендуемый интерфейс

Логика может быть оформлена как PostgreSQL function/RPC либо строго атомарный service layer.

Концептуально:

```text
resolve_nearest_lesson_start(
  tutor_id,
  student_id,
  desired_start,
  duration_minutes,
  ignore_lesson_id?
) -> actual_start
```

`ignore_lesson_id` нужен при переносе/редактировании, чтобы занятие не конфликтовало само с собой.

## 4.2. Проверяемые интервалы

Конфликт:

```text
existing.starts_at < candidate.end
AND existing.ends_at > candidate.start
```

Исключить текущий lesson при update.

Проверять:

- все занятия tutor;
- все занятия student.

## 4.3. Безопасность

Не отдавать репетитору данные чужого занятия ученика:

- нельзя возвращать `id`, имя второго tutor, предмет или заметку чужого занятия;
- наружу возвращается только фактическое выбранное время или общая ошибка отсутствия слота.

## 4.4. Race condition

Даже после предварительного расчёта insert/update может столкнуться с параллельной записью.

Требуется:

- выполнять resolve + write в транзакции;
- на exclusion violation допустимо повторить поиск ограниченное число раз;
- после исчерпания retry вернуть контролируемую ошибку toast, не raw PostgreSQL error.

# 5. Изменения клиентской архитектуры расписания

## 5.1. Один набор данных

`ScheduleData.lessons` должен содержать все занятия пользователя, а `week` оставаться только состоянием отображения.

## 5.3. Навигация

`navigate()`:

- меняет query string через History API;
- меняет active/mobile date;
- не вызывает `router.refresh()`.

`popstate`:

- должен только восстановить отображаемую неделю/день;
- не должен принудительно перезагружать серверные данные.

## 5.4. Мутации

После успеха Server Action обновлять один объект/массив локально.

Пример:

- create → `setLessons(prev => [...prev, returnedLesson])`;
- update/move → replace по `id`;
- delete → filter ids;
- complete/color → patch объекта.

При ошибке optimistic state откатывается и показывается toast.

## 5.5. Выделение

После create:

- выбрать новое занятие;
- перейти к фактическому дню/неделе только если это не нарушает FR-13;
- не сбрасывать весь grid.

# 8. Изменение правил валидации

## 8.1. Дата занятия

`lessonSchema` не должен считать произвольную валидную ISO-дату достаточной для create.

- update/move не переносит запись в будущую неделю;
- day value принадлежит допустимой неделе диалога.

Нельзя доверять данным custom Select с клиента.

## 8.2. Предмет и назначение

Для новых занятий проверять одновременно:

- student существует и имеет роль `student`;
- subject существует;
- subject доступен;
- существует актуальная `student_tutor_assignments` для комбинации student + tutor + subject;
- tutor имеет этот предмет.

Удалённый subject не может участвовать в новом lesson.

# 13. Производительность

Несмотря на требование загружать всю историю, реализация не должна создавать искусственные O(N²) операции на каждом render.

Требования:

- DB чтение пакетами;
- conflict checks выполняются SQL по индексам, а не загрузкой всей БД в JS;
- для клиентского отображения допустима memoization/indexing по неделям;
- при переключении недели не пересоздавать дорогие структуры без необходимости;
- список из тысяч lessons должен оставаться управляемым.

Если потребуется виртуализация dropdown списков людей — допускается, но визуально она не должна отличаться от обычного списка.

# 14. Безопасность и приватность

Сохранить текущие принципы проекта:

- student не может изменять расписание;
- tutor/admin изменяют только собственный календарь;
- admin не получает право редактировать календарь другого tutor только из-за роли admin;
- private note не отдаётся ученику;
- magnet не раскрывает данные чужих занятий ученика;
- hard delete subject доступен только admin;
- cron rollover не должен обходить бизнес-валидаторы назначения/предмета;
- никаких service-role credentials на клиенте.

# 18. Не входит в это ТЗ

Чтобы не расширять scope:

# 19. Итоговое ожидаемое поведение расписания

Пользователь открывает расписание один раз и получает всю свою историю. Переключение по годам, месяцам и неделям происходит мгновенно без повторной загрузки таблицы. В текущей неделе tutor/admin может создавать и редактировать занятия. Если выбранное время занято, система сама «примагничивает» занятие к ближайшему свободному 5-минутному слоту, не допуская пересечений ни у tutor, ни у student. Любая мутация обновляет только нужную карточку и подтверждается toast.

Будущую неделю можно открыть, но нельзя заполнять вручную. Когда по локальному времени владельца начинается новая неделя, система автоматически создаёт в ней новые запланированные копии валидных занятий прошлой недели. Прошлая неделя остаётся неизменной в истории и статистике. Удалённые предметы больше не существуют в текущих данных, но старые занятия продолжают отображать их историческое название.
