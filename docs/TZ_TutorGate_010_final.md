# ТЗ: TutorGate — пакет 010

**Проект:** TutorGate v2  
**Дата:** 06.09.2026  
**Статус:** готово к реализации  
**Основание:** текущий архив проекта `tutorgate-v2(5).zip`, скриншот №1 со стилем переключателя периода, скриншот №2 с лишним вертикальным отступом и подтверждённые требования заказчика.

---

## 1. Цель пакета

В пакете 010 необходимо:

1. унифицировать курсор при наведении на поля даты и времени;
2. сделать раздел «Заявки» компактнее и привести его переключатели к стилю segmented control со скриншота №1;
3. убрать чрезмерный вертикальный отступ в статистике со скриншота №2;
4. добавить администратору массовую синхронизацию Telegram username;
5. расширить админские списки учеников и репетиторов логином TutorGate, Telegram ID и Telegram username и добавить поиск по этим данным;
6. добавить администратору смену роли `student ↔ tutor`, блокировку/разблокировку и безопасное удаление аккаунта с сохранением истории;
7. расширить контекстное меню расписания командами «Копировать», «Вставить» и «Создать занятие здесь»;
8. сделать клавиатурные сочетания расписания независимыми от русской/английской раскладки.

Все изменения должны сохранять текущую архитектуру проекта: Next.js App Router, React, strict TypeScript, Supabase/PostgreSQL, RLS, Server Actions, server-only доступ к service role и Telegram Bot API.

---

## 2. Зафиксированные решения заказчика

Следующие решения считаются подтверждёнными и не требуют дополнительного согласования:

- обе группы фильтров в «Заявках» должны использовать стиль переключателя со скриншота №1;
- на desktop обе группы фильтров должны располагаться **в одну строку**;
- в настройках нужна одна массовая кнопка **«Синхронизировать всех»**;
- если Telegram username у пользователя удалён, сохранённый старый username также необходимо удалить;
- «назначить ученика репетитором и снять» означает **смену одной роли на другую**, а не двойную роль;
- смену роли необходимо запрещать, пока у пользователя есть несовместимые активные связи;
- блокировка означает: запрет входа, немедленное завершение активных сессий, сохранение данных и возможность разблокировки;
- заблокированный пользователь остаётся видимым администратору;
- удаление аккаунта выполняется безопасно: доступ и персональные данные удаляются/обезличиваются, история занятий и статистика сохраняются;
- «создать задание здесь» означает **«Создать занятие здесь»**;
- поиск в админских списках должен работать одной строкой по ФИО, логину TutorGate, Telegram username и Telegram ID;
- `cursor: text` применяется только к полям даты/времени при наведении на них, без глобального изменения курсора для остальных элементов;
- в пустом месте расписания пункт `Вставить` показывается только тогда, когда во внутреннем clipboard уже есть скопированные занятия.

# 4. TG-010-01 — курсор для полей даты и времени

## 4.1. Требование

При наведении непосредственно на поля даты и времени курсор должен быть текстовым I-beam (`cursor: text`), как у обычного текстового input.

## 4.2. Реализация

В общих стилях заменить текущее правило для date и добавить time:

```css
input[type="date"],
input[type="time"] {
  cursor: text;
}
```

Для нативных индикаторов календаря/времени также установить `cursor: text` там, где браузер позволяет это сделать, чтобы при нахождении указателя внутри такого поля курсор визуально не переключался обратно на pointer.

Не применять это правило к `button`, `select`, segmented controls, карточкам расписания и другим интерактивным элементам.

## 4.3. Ограничения

- не менять нативную работу date/time picker;
- не вызывать `showPicker()` автоматически;
- не менять accessibility и tab navigation;
- не менять курсор вне date/time inputs.

## 4.4. Acceptance criteria

- при наведении на любое `input[type="date"]` курсор — I-beam;
- при наведении на любое `input[type="time"]` курсор — I-beam;
- дата/время по-прежнему вводятся и выбираются штатным способом;
- остальные элементы интерфейса не меняют cursor-поведение.

# 5. TG-010-02 — компактный раздел «Заявки»

## 5.1. Страница

`/admin/applications`

## 5.2. Новый layout фильтров

Сейчас используются два отдельных `<nav className="application-tabs">` один под другим.

Необходимо обернуть обе группы в общий toolbar, например:

```text
[ Ученики | Репетиторы ]   [ На рассмотрении | Принятые | Отклонённые ]
```

### Desktop

При ширине `>= 768px`:

- обе группы находятся в одной строке;
- между группами компактный gap около `8–10px`;
- не растягивать группы по всей ширине страницы;
- не создавать между ними большое пустое пространство;
- перенос на вторую строку на обычном desktop не допускается.

### Mobile

При недостаточной ширине:

- разрешить перенос групп на следующую строку;
- каждая segmented-группа остаётся цельным визуальным блоком;
- не допускать horizontal overflow страницы;
- при необходимости допустим горизонтальный scroll внутри конкретной группы, но предпочтительно компактное адаптивное размещение.

## 5.3. Стиль переключателей

Визуально повторить `.period-tabs` со скриншота №1:

- общий контейнер для группы;
- `background: var(--surface)`;
- `border: 1px solid var(--border)`;
- `border-radius: 7px`;
- внутренний padding примерно `3px`;
- отдельные неактивные пункты без собственной внешней рамки;
- текст неактивного пункта — muted;
- активный пункт — `background: var(--surface-raised)` + основной foreground;
- внутренний radius активного пункта около `4px`;
- компактная типографика уровня `.period-tabs`;
- ориентир padding пункта: `7px 10px`;
- не использовать `min-height: 44px` для desktop tab;
- сохранить `aria-current="page"`;
- сохранить заметный `focus-visible`.

Рекомендуется не копировать стили вручную в нескольких местах, а вынести общий segmented-control паттерн либо использовать общие CSS-токены/классы.

## 5.4. Компактность карточек заявок

Изменить существующие размеры:

### Desktop

- `.application-card`: `padding` ориентировочно `16–18px` вместо `24px`;
- `.application-list`: `gap` `10–12px` вместо `16px`;
- `.application-card-heading`: gap `10–12px`;
- заголовок заявки: около `16px` вместо `18px`;
- `.application-details`: `margin` около `14–16px 0` вместо `24px 0`;
- `.application-details`: вертикальный gap около `10–12px`;
- кнопки действий — компактная desktop-высота порядка `36–38px`;
- убрать принудительный `.applications-page .button { min-height: 44px; }` на desktop.

### Mobile

- card padding `14–16px`;
- сохранить удобную touch-зону кнопок;
- детали можно оставить одной колонкой;
- длинные ФИО, usernames, цели и опыт должны переноситься без выхода за viewport.

## 5.5. Что не менять

- бизнес-логику модерации;
- статусы заявок;
- серверные фильтры;
- пагинацию;
- тексты и данные самой заявки, кроме визуального уплотнения.

## 5.6. Acceptance criteria

- обе группы переключателей находятся в одной строке на desktop;
- стиль совпадает по принципу со скриншотом №1;
- активное состояние задаётся заливкой внутри общей рамки, а не отдельной accent-рамкой каждой кнопки;
- карточки визуально заметно компактнее текущих;
- на экране помещается больше заявок при сохранении читаемости;
- 320/375px не дают horizontal overflow.

# 6. TG-010-03 — убрать большой отступ в статистике

## 6.1. Проблема

На скриншоте №2 между верхней строкой фильтров статистики и KPI-карточками находится чрезмерно большой пустой вертикальный блок.

Причина в текущем desktop-правиле:

```css
.statistics-page .statistics-controls {
  min-height: 120px;
}
```

При обычном режиме без кастомных дат контент фильтров занимает примерно одну строку, но контейнер принудительно резервирует 120px высоты.

## 6.2. Требуемое исправление

Для desktop убрать фиксированную минимальную высоту `120px`.

Контейнер `.statistics-controls` должен иметь высоту по фактическому содержимому.

Оставить нормальный нижний отступ между контролами и KPI-блоком — ориентир `20–24px`.

При выборе `Свой период` строка с датами должна увеличивать высоту контейнера естественным образом, без наложений и без искусственного пустого пространства.

Не исправлять проблему отрицательным margin.

## 6.3. Acceptance criteria

- при режимах `7 / 14 / 30 дней` KPI-карточки находятся примерно через `20–24px` после строки фильтров;
- пустого блока высотой около 100px больше нет;
- `Свой период` не ломает layout;
- desktop и mobile остаются scrollable при недостатке высоты;
- chart/KPI блоки не перекрываются с контролами.

# 7. TG-010-04 — массовая синхронизация Telegram username

## 7.1. Страница

`/admin/settings`

## 7.2. UI

Добавить третью settings-card «Telegram».

Состав:

- иконка Telegram/синхронизации в текущем стиле панели;
- заголовок: `Telegram`;
- описание: `Обновляет актуальные Telegram username у привязанных аккаунтов.`;
- кнопка: **`Синхронизировать всех`**;
- loading state: `Синхронизируем…`;
- повторный клик во время операции блокируется.

После завершения показать toast или inline-result формата:

```text
Проверено: 42 · Обновлено: 5 · Username удалён: 2 · Без изменений: 34 · Ошибки: 1
```

## 7.3. Источник данных Telegram

Для каждого не удалённого пользователя с сохранённым `telegram_chat_id` выполнить server-only запрос Telegram Bot API `getChat` по постоянному chat ID.

Нельзя искать пользователя по старому username: username изменяемый, а `telegram_chat_id`/`telegram_user_id` являются постоянной связкой аккаунта.

## 7.4. Обновление username

Если Telegram возвращает:

- новый username — записать его в `profiles.telegram_username`;
- тот же username — ничего не менять;
- отсутствие username — очистить `profiles.telegram_username` (`NULL`);
- ошибку по конкретному пользователю — продолжить обработку остальных и увеличить счётчик ошибок.

Синхронизация не должна менять:

- логин TutorGate;
- Telegram ID;
- Telegram chat ID;
- роль;
- ФИО.

## 7.5. Изменение схемы для отсутствующего username

Сейчас `profiles.telegram_username` имеет `NOT NULL`.

Для корректного отражения состояния «username отсутствует» в package 010 необходимо разрешить `NULL`:

```text
profiles.telegram_username: text null
```

Все места, которые сейчас предполагают обязательный username, должны быть адаптированы:

- admin directory;
- ссылка `https://t.me/...`;
- `visible_profiles()`;
- типы TypeScript;
- отображение профиля;
- password recovery lookup.

Если username отсутствует:

- показывать `Нет username`;
- не формировать ссылку `https://t.me/null`/`https://t.me/undefined`;
- старое значение не сохранять как «последнее известное».

## 7.6. Ограничение параллелизма

Не запускать запрос ко всем пользователям через неограниченный `Promise.all`.

Использовать batches или ограниченный concurrency, ориентир — не более 5 одновременных запросов Telegram API.

Один timeout/error не должен отменять уже успешные обновления других пользователей.

## 7.7. Безопасность

- action только для `admin`;
- повторная проверка роли на сервере обязательна;
- `TELEGRAM_BOT_TOKEN` никогда не отправляется в browser bundle;
- не логировать bot token;
- не возвращать в клиент полные сырые Telegram payloads.

## 7.8. Acceptance criteria

- кнопка видна только администратору в настройках;
- после смены @username в Telegram синхронизация обновляет запись;
- после удаления username в Telegram старый username очищается;
- ошибка одного аккаунта не блокирует остальных;
- итоговый результат сообщает количество успешных/неуспешных проверок.

# 8. TG-010-05 — служебные идентификаторы и поиск в «Учениках»/«Репетиторах»

## 8.1. Страницы

- `/admin/students`
- `/admin/tutors`

## 8.2. Данные у пользователя

Для администратора рядом с ФИО показывать компактный служебный блок:

```text
Логин: ivan_petrov
Telegram: @ivanpetrov
Telegram ID: 123456789
```

Если username отсутствует:

```text
Telegram: Нет username
```

У заблокированного пользователя показывать отдельный badge:

```text
Заблокирован
```

## 8.3. Логин TutorGate

Источник логина — `private.auth_aliases.username_normalized`.

Не добавлять логин в общий `visible_profiles()`.

Не раскрывать login/Telegram ID ученикам или репетиторам через общий RPC.

## 8.4. Отдельный admin-only контракт

Добавить отдельный безопасный контракт для admin directory, например security-definer RPC:

```text
admin_directory_profiles()
```

Возвращаемые поля:

- `id`;
- `role`;
- `full_name`;
- `login`;
- `telegram_username`;
- `telegram_user_id`;
- `account_status`;
- при необходимости `blocked_at`.

RPC обязан внутри функции проверить, что `auth.uid()` имеет `profiles.role = 'admin'`.

`EXECUTE` не должен быть доступен `anon`.

Для не-admin страниц продолжить использовать узкий `visible_profiles()`.

В TypeScript создать отдельный тип, например `AdminDirectoryProfile`; не расширять без необходимости публичный `Profile` приватными полями.

## 8.5. Поиск

Одна существующая строка поиска должна искать одновременно по:

1. ФИО;
2. логину TutorGate;
3. Telegram username;
4. Telegram ID.

Новый placeholder:

```text
Поиск по имени, логину, @username или Telegram ID…
```

Новый `aria-label` должен отражать все варианты поиска.

### Нормализация

- trim;
- case-insensitive для ФИО/login/username;
- начальный `@` у Telegram username игнорируется;
- Telegram ID обрабатывается как строка, не преобразуется в JS number;
- допускается поиск по подстроке.

Примеры:

- `ivan` → ФИО/login/username;
- `@ivan_petrov` → username;
- `ivan_petrov` → login и username;
- `123456789` → Telegram ID.

## 8.6. Telegram link

Если `telegram_username` есть — оставить `Открыть Telegram`.

Если username отсутствует:

- ссылку не рендерить;
- вместо неё можно показать muted-текст `Нет Telegram username`;
- Telegram ID всё равно остаётся видимым администратору.

## 8.7. Acceptance criteria

- admin видит login + Telegram username + Telegram ID;
- student/tutor не получают эти дополнительные данные через свои директории;
- существующий поиск по ФИО работает;
- поиск по логину работает;
- поиск по `@username` и username без `@` работает;
- поиск по Telegram ID работает;
- отсутствие Telegram username не ломает строку пользователя и не создаёт невалидную t.me-ссылку.

# 9. TG-010-06 — смена роли, блокировка и безопасное удаление аккаунта

## 9.1. Общий UI

В колонке «Управление» у `student` и `tutor` добавить компактное меню действий пользователя, чтобы не перегружать строку кнопками.

Рекомендуемый вид — кнопка `⋯` / `Действия` с меню:

### Для ученика

- `Сделать репетитором`;
- `Заблокировать` / `Разблокировать`;
- `Удалить аккаунт`.

### Для репетитора

- `Сделать учеником`;
- `Заблокировать` / `Разблокировать`;
- `Удалить аккаунт`.

Пользователи с `role = admin` не должны менять роль, блокироваться или удаляться через этот UI в рамках package 010.

## 9.2. Новое состояние аккаунта

Рекомендуется добавить единое состояние:

```text
account_status = active | blocked | deleted
```

Например:

```text
public.account_status enum ('active', 'blocked', 'deleted')
profiles.account_status not null default 'active'
profiles.blocked_at timestamptz null
profiles.blocked_by uuid null
profiles.deleted_at timestamptz null
profiles.deleted_by uuid null
```

Это предпочтительнее комбинации нескольких независимых boolean-флагов.

## 9.3. Блокировка

При `Заблокировать`:

1. показать confirmation dialog с ФИО и логином;
2. установить `account_status = 'blocked'`;
3. записать `blocked_at`, `blocked_by`;
4. вызвать существующий server-only `revoke_user_sessions(user_id)`;
5. текущие активные сессии пользователя перестают работать;
6. новый вход блокируется;
7. история занятий, статистика, заявки и назначения не удаляются;
8. пользователь остаётся видимым администратору с badge `Заблокирован`;
9. пользователь не должен предлагаться для новых назначений/новых занятий, пока заблокирован.

При `Разблокировать`:

- вернуть `account_status = 'active'`;
- очистить `blocked_at`, `blocked_by`;
- новый вход снова разрешён.

Разблокировка не восстанавливает удалённый аккаунт.

## 9.4. Проверка blocked/deleted при авторизации

Текущий `loginAction` после Supabase sign-in получает только `role`.

Необходимо добавить проверку `account_status`.

Пользователь со статусом `blocked` или `deleted` не должен получать рабочую TutorGate-сессию.

Важно: не привязывать новый opaque handle через `bind_session` до подтверждения, что аккаунт активен, либо немедленно удалить созданную сессию при отказе.

Также server-side access layer (`currentProfile` / `requireRole`) должен fail closed для уже существующей/устаревшей сессии заблокированного пользователя.

Таким образом блокировка работает не только через скрытие UI, но и на сервере.

## 9.5. Смена роли

Роль остаётся одиночной.

Допустимые изменения:

```text
student -> tutor
tutor -> student
```

`admin` через этот UI не изменяется.

Операция должна выполняться через одну транзакционную security-definer RPC/серверную команду, а не серией независимых client-side запросов.

### 9.5.1. Student → Tutor

Смена запрещена, если существуют несовместимые активные данные:

- строки `student_tutor_assignments`, где пользователь является `student_id`;
- текущие или будущие занятия, где пользователь является учеником (`ends_at >= now()`);
- иные активные связи, из-за которых текущие DB role-checks перестанут быть корректными.

Исторические завершённые занятия из прошлого сохраняются.

После удаления администратором активных назначений и отсутствия будущих занятий роль можно сменить.

Технические вспомогательные записи доступности, относящиеся только к прежней роли и не являющиеся историей, можно очистить внутри транзакции смены роли.

### 9.5.2. Tutor → Student

Смена запрещена, если существуют:

- `student_tutor_assignments`, где пользователь является `tutor_id`;
- `tutor_subjects`;
- текущие или будущие занятия, где пользователь является репетитором (`ends_at >= now()`);
- другие активные role-specific связи.

До смены администратор должен:

1. снять назначения учеников;
2. снять предметы репетитора;
3. убрать/перенести будущие занятия.

Исторические занятия остаются в БД.

После успешной смены tutor-only operational state, не являющийся историей, может быть очищен автоматически.

## 9.6. Ошибка смены роли

Вместо generic `Не удалось сохранить` показывать конкретную причину, например:

```text
Нельзя сделать пользователя репетитором: сначала снимите 2 назначения и уберите 3 будущих занятия.
```

или:

```text
Нельзя сделать пользователя учеником: сначала снимите предметы репетитора и назначения учеников.
```

## 9.7. Безопасное удаление аккаунта

Физически удалять `auth.users`/`profiles` нельзя, если это уничтожит или разорвёт исторические связи.

Удаление в package 010 означает **необратимое обезличивание + отзыв доступа**, при этом запись-технический идентификатор остаётся для FK истории.

### При подтверждении `Удалить аккаунт`:

1. показать destructive confirmation dialog;
2. установить `account_status = 'deleted'`;
3. заполнить `deleted_at`, `deleted_by`;
4. отозвать все активные sessions;
5. удалить запись пользователя из `private.auth_aliases`, чтобы старый TutorGate login больше не разрешался;
6. инвалидировать/удалить активные password reset tokens пользователя;
7. очистить персональные Telegram данные;
8. обезличить ФИО;
9. очистить auth user metadata, содержащую username/registration metadata, через server-only Admin API;
10. скрыть пользователя из обычных списков и новых assignment/selectors;
11. сохранить историю занятий и статистику.

### Персональные поля после удаления

Для нормальной модели данных package 010 рекомендуется разрешить nullable для:

```text
profiles.telegram_username
profiles.telegram_user_id
profiles.telegram_chat_id
```

После удаления:

```text
full_name = 'Удалённый пользователь'
telegram_username = NULL
telegram_user_id = NULL
telegram_chat_id = NULL
```

`id` профиля сохраняется как технический FK истории.

`private.auth_aliases` для удалённого аккаунта отсутствует.

Если из-за особенностей текущей Auth-схемы физический `auth.users` необходимо сохранить, он остаётся технической tombstone-записью без рабочего логина в TutorGate.

## 9.8. История после удаления

Существующие lessons/statistics не удалять.

В исторических занятиях пользователь отображается как `Удалённый пользователь`, если запрос использует текущее `profiles.full_name`.

Не выполнять cascade delete истории ради удаления аккаунта.

## 9.9. Ограничения безопасности

- все user-management действия только для `admin`;
- повторная проверка admin-role внутри RPC/action;
- нельзя позволить пользователю изменить/заблокировать/удалить `admin` через новый UI;
- роль нельзя менять простым client-side `update profiles`;
- удаление необратимо через обычный UI;
- блокировка и удаление обязательно отзывают opaque sessions.

## 9.10. Acceptance criteria

### Роль

- student без активных несовместимых связей успешно становится tutor;
- tutor без активных несовместимых связей успешно становится student;
- при наличии назначений/предметов/будущих занятий смена роли отклоняется;
- история прошлого не удаляется;
- admin-role нельзя изменить через новый интерфейс.

### Блокировка

- после блокировки текущая активная сессия перестаёт работать;
- новый login не даёт войти;
- пользователь виден admin с badge;
- после разблокировки вход снова работает.

### Удаление

- старый TutorGate login больше не работает;
- активные sessions отозваны;
- Telegram identifiers очищены;
- ФИО обезличено;
- пользователь не предлагается в новых назначениях;
- исторические занятия и агрегированная статистика сохраняются.

# 11. TG-010-08 — бинды независимо от раскладки клавиатуры

## 11.1. Проблема

Сейчас используется:

```ts
const key = event.key.toLowerCase();
```

При русской раскладке физические клавиши C/V/Z возвращают кириллические символы, поэтому сочетания не совпадают с `c`, `v`, `z`.

## 11.2. Требуемое решение

Для буквенных shortcut использовать `KeyboardEvent.code`:

```text
KeyC -> Copy
KeyV -> Paste
KeyZ -> Undo
Shift + KeyZ -> Redo
```

Модификатор:

```ts
event.ctrlKey || event.metaKey
```

сохранить.

Пример логики:

```ts
if (event.code === "KeyZ") ...
if (editable && event.code === "KeyC") ...
if (editable && event.code === "KeyV") ...
```

## 11.3. Важные ограничения

Сочетания не перехватываются, если focus находится внутри:

- `input`;
- `textarea`;
- `select`;
- `[contenteditable]`;
- combobox;
- dialog.

Сохранить текущие проверки lock/pending/role.

## 11.4. Поведение

При физическом нажатии `Ctrl+C` на клавише C команда должна работать одинаково при:

- EN layout;
- RU layout.

То же для V и Z.

## 11.5. Окно «Бинды»

Визуальные подписи оставить привычными:

```text
Ctrl+C
Ctrl+V
Ctrl+Z
Ctrl+Shift+Z
```

Добавить/уточнить действия контекстного меню при необходимости, но пользователю не нужно показывать `KeyC`/`KeyV`.

## 11.6. Acceptance criteria

- copy работает на RU и EN;
- paste работает на RU и EN;
- undo работает на RU и EN;
- redo работает на RU и EN;
- ввод текста в полях не перехватывается;
- Meta-сочетания продолжают работать там, где они поддерживались раньше.

при:

- screenshots/regression tests подтверждают устранение отступа в статистике и новый вид заявок;
- обновлены документы проекта при изменении контрактов:
  - `docs/database.md`;
  - `docs/auth-and-telegram.md`;
  - `docs/verification.md`;
  - при необходимости `docs/architecture.md`.

Если конкретную проверку невозможно выполнить в среде разработки, это явно записывается в verification; непроверенный пункт нельзя отмечать как успешно пройденный.

# 16. Что не входит в package 010

Не включать без отдельного ТЗ:

- одновременную двойную роль student+tutor;
- отдельную сущность домашнего задания из контекстного меню;
- массовое физическое удаление исторических занятий;
- индивидуальную кнопку Telegram sync в каждой строке пользователя;
- изменение Telegram ID/chat ID по username;
- управление администраторами через новый user-actions menu;
- сохранение clipboard расписания между перезагрузками браузера/сессиями.
